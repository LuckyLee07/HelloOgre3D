# 设计探索

供 [共享工作流](workflow.md) 在需求或架构存在实质选择时使用。

先对照项目方向、相关模块和当前源码说明目标、约束与可观察的验收结果。常规选择直接给推荐方案；有实质成本/行为差异才比较备选。只询问会改变结果且无法从上下文推断的信息，相关问题可合并。

设计写清涉及的层、数据/所有权边界、失败语义和受影响 sample，篇幅与复杂度相称。不要为假想编辑器/UGC 扩展范围。

用户要求 spec 或跨模块工作需要持久设计时，写 `docs/dev-design/specs/<YYYY-MM-DD>-<topic>-design.md`，包含日期、状态、目标、方案和验收；无需作者身份或空模板章节。校验范围与内部一致性，未决问题如实保留。

只要设计就交付设计；已有实现授权就继续。仅显式 gated 模式在完整 spec 可供审阅后等 Gate 1，不逐节请求确认。
