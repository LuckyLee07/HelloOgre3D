# 项目方向与长期演进设计

> 本文是 HelloOgre3D 的方向真源。2026-09-05 根据用户明确的“自己的个人项目”定位修订。
> 2026-09-10 补充：玩法收敛与整体视觉设计见 §1.3，M2/M3 研究设计见 §5；两条路线按当前问题独立认领，实际状态以 cycle/backlog 为准。
> 本文定义方向、目标、阶段依赖和设计边界；当前执行情况看 [cycle-01.md](cycle-01.md)，任务状态看 [backlog.md](backlog.md)。
> 这里的里程碑是后续设计，不代表对应代码已经实现。2026-09-10 的中继站实现与验证另见 [当前试玩记录](playtest-relay-2026-09-10.md)，不以设计文字代替运行证据。

## 1. 项目定位

HelloOgre3D 是一个长期维护的个人游戏 AI 与玩法实验项目。通过可运行的 3D 场景，探索智能体的感知、记忆、决策、运动和协作，逐步积累可观察、可验证、可复用的 C++ / Lua 玩法基础设施。

主要收益是个人学习、技术深入和创作体验。可玩原型用于检验技术、干预 AI 行为和探索自己的兴趣；游戏发行、外部玩家、商业化和最终品类均为未来选择，不是当前阶段完成的前提。

**核心方向：以游戏 AI 为主线，建设一个自己能玩、能观察、能实验的 3D 沙盒。**

“生产级”用于约束具体模块的质量：所有权清楚、接口边界合理、故障可诊断、性能有依据、行为能验证。不要求个人项目最终覆盖完整商业引擎、编辑器或内容生产链。

### 1.1 取舍顺序

1. 能帮助理解一个具体 AI 问题，或实现一个自己想尝试的行为。
2. 能在现有场景中运行、观察和比较。
3. 能降低下一次实验、调试或维护的成本。
4. 在以上基础上，提炼经过实际使用验证的公共能力。

个人兴趣可以成为选题理由，但应写成一个可回答的问题。例如“想研究动态导航”应收敛为“门关闭后，士兵如何发现路径失效并重新选择路线”。小实验有结论即可，不必自动升级为完整系统。

### 1.2 成功标准

- 学习：能解释机制及其取舍，并用场景验证自己的理解。
- 创作：能亲自干预场景，观察行动的后果，产生下一次想尝试的策略。
- 工程：留下可运行的 sample、可复现的实验或可再次使用的模块。
- 持续性：暂停后能凭简短记录恢复工作，项目规模在个人可维护范围内。

不把 sample 数量、代码行数、框架数量、外部试玩人数和固定日历交付次数作为成功指标。作者体验可以证明个人偏好；陌生人的上手难度和大众接受度在没有外部证据时保持未知。

### 1.3 近期重点：玩法收敛与整体视觉设计

围绕 Sandbox19 的一场小队战术任务，同时收敛操作、规则、关卡、场景美术、UI 与视听反馈，形成从进入到结算重试的完整体验。视觉品质是本阶段主目标之一：先建立目标画面，在游戏内第一版就落实代表性的场景与 HUD 效果，后续持续对照，不等全部功能完成后再补美术。

首版以一张小地图、现有两名 AI 队友和一项主要任务为范围起点。用户已明确反馈：“这套玩法与视觉都非常棒，就按照这套实施吧”。伴随式小队指挥、中继站短任务、浅暖工业场景与紧凑 HUD 已获批准，P1–P3 持续实施，无需再次等待方向确认。具体参数与手感继续通过画面和实际操作验证。个人项目定位保持，产品化在这里指体验完整、规则可信、视觉一致与运行可靠，不以商业发行或外部用户为前提。

近期顺序为共同设计 → 游戏内首版 → 整场体验 → 完成度与独立运行收口。研究路线 M2/M3 按需继续，其中最小比较记录可服务本阶段；大规模 AI 扩展、完整回放和全面架构清理不作为前置。具体产物、依赖和验收见 [联合推进计划](dev-design/plans/2026-09-10-sandbox19-product-experience.md)。

## 3. 长期目标与能力边界

| 目标 | 期望状态 | 可检验的成果 |
|---|---|---|
| G1：深入理解游戏 AI | 能解释并调整角色如何感知、记忆、决策、移动和协作 | 一个问题对应一个对照实验，说明结论和适用条件 |
| G2：持续演进的可玩场景 | 综合场景支持自己操控、指挥、观察并测试新想法 | 新能力对场景行为产生可见影响，能正常开始、结束和重开 |
| G3：方便实验与诊断 | 能记录条件、定位异常、比较行为与成本 | 可重复执行同一实验，分辨算法效果、随机波动和环境差异 |
| G4：可靠的工程积累 | 公共能力有边界、生命周期与验证依据 | 第二个场景接入更容易，已有 sample 保持可运行 |

四者不是四条同时开工的项目线。AI 是主线，场景是载体，观测与工程为正在研究的问题提供支撑。

### 3.1 Sample 策略

- Sandbox19 是综合实验场，承载成熟能力的组合和操控体验；不要求所有实验都接入它。
- Sandbox6/7/8 等保留为决策模型的学习与回归场景，避免混入无关玩法。
- Sandbox12 优先承载团队记忆的隔离实验；Sandbox17/18 承载战术与影响力地图实验。
- 能通过现有 preset 表达的变化优先用 preset；只有隔离条件或场景目标明显不同时才新增 sample。
- 专题实验先证明能力，进入综合场景时再验证交互。综合场景中的胜负不能代替子系统正确性检查。

### 3.2 架构策略

保持依赖方向：Engine/External → runtime → sandbox → game/client → Lua scripts/samples。

- C++ 负责感知扫描、空间查询、导航、战术计算等热点，以及稳定的运行时与生命周期边界。
- Lua 负责实验布局、preset、行为配置、指令编排和可读的实验流程。
- 引擎 UI、输入和绘制适配放 runtime；AI 诊断数据由 sandbox 提供，界面不反向操控组件内部状态。
- 复用 Blackboard、TeamBlackboard、现有事件设施与 AI driver；不为观测或回放创建第二套决策系统。
- 若新增 Lua API，同步 `.pkg`、生成绑定、调用点和相关 sample。不得假定 C++ 声明等同于 Lua 已导出。
- 架构改动由实验或维护问题触发，不把清空全部历史技术债设为开发前提。

## 4. 阶段路线：按证据推进，不写远期日历承诺

| 阶段 | 核心问题 | 最小产物 | 退出条件 |
|---|---|---|---|
| A：掌握现有链路 | 士兵为什么采取这个行为？ | 一个士兵的行为证据链，及能重复执行的基础实验 | 能定位代表性异常，并区分事实与解释 |
| B：做深一个主题 | 团队共享到底改变了什么？ | 共享开启/关闭的对照场景与结论 | 行为差异有证据；没有差异也能解释原因 |
| C：按兴趣扩展 | 下一个值得研究的问题是什么？ | 导航、战术、玩法或性能中的一个专题实验 | 问题得到回答，或明确记录边界后停止 |
| D：验证复用 | 实验能力能否在另一场景使用？ | 第二使用场景和最小模块说明 | 不复制整套实现也能接入，回归面保持可运行 |

A/B 是研究路线的推荐顺序；当前体验改版优先级见 §1.3。C/D 可以往复，不要求一次通过后永远结束。完整回放不是所有实验的前置条件：基础配置记录和直接事件检查能回答问题时，先使用它们。

## 5. 近期详细设计

### M1：解释一次完整 AI 行为

**问题：** 当一个士兵不移动、不攻击、换目标或忽略指令时，如何区分感知、记忆、决策、导航和执行问题？

**最小场景：** 先在 Sandbox19 选中一个士兵，覆盖自主接敌、玩家集火、目标丢失、指令过期四种过程。先核对既有意图卡、BT trace、RuntimeDiag；只补缺失信息及关联。

建议的诊断语义如下，属于设计字段而非已存在接口名：

| 信息 | 最少内容 | 数据来源与约束 |
|---|---|---|
| 身份 | agent id、profile、控制来源、仿真时间 | 对象和 controller；对象重建后旧选中状态失效 |
| 感知 | 当前目标、是否直接可见、最近观察时间 | 既有感知结果；UI 不重新扫描 |
| 记忆 | 最后已知位置、来源、自身/团队信息、时效 | Blackboard / TeamBlackboard；共享信息不标成直接看见 |
| 指令 | 类型、目标、剩余 TTL、失效原因 | 既有命令状态；过期、死亡、清理可区分 |
| 决策 | 活跃节点/动作、目标选择依据 | 既有 BT trace 与实际分支；缺证据时标未知 |
| 执行 | 移动目标、攻击状态、请求失败或受阻信息 | 组件/导航实际状态；不要根据静止画面推断失败 |

**实施切分：** 先列出可读取的信息与缺口 → 用现有文本/诊断输出验证语义 → 再补选中单位的可视表达 → 验证目标死亡与重开清理。首版不做通用编辑器、不强制替换现有 UI 技术。

**开销与存储：** 默认只观察选中单位；状态转换时记录事件，连续状态采用有上限的采样。若增加历史记录，使用有限容量并报告截断。显示刷新与 AI tick 解耦，关闭调试后避免额外全量扫描。

**验收：** 对四种过程分别留下“实际状态—可见表达—依据”记录；过期指令不再显示活跃；失去视野后能区分记忆与当前可见；重开不引用旧对象。实现中未能获取的原因明确记为缺口，不从最终动作编造决策理由。

### M2：重复一个实验并比较结果

**问题：** 改动一个参数后，行为变化来自该参数，还是版本、平台、随机性、物理和场景干预？

**首版范围：** 固定场景条件与实验元数据、关键事件输出、成对运行摘要。需要重放指令才能定位的问题出现后，再实现语义指令回放；不先做完整键鼠录制、世界快照或跨版本回放。

实验记录最少包含：

- run id、代码版本及工作区是否有未提交改动、平台/架构、Debug/Release。
- sample、preset、配置内容或可核对指纹、seed、仿真步长和调度配置。
- 场景初始布局、双方单位配置、实验变量、关卡导演开关。
- 关键指令、事件的仿真时间或 tick、摘要结果、失败/中断原因。

只记录 dirty 标记不足以复原未提交代码；需要重复的实验应关联可恢复的本地版本或保留局部 diff。配置指纹也不能替代原始配置，必须能找到对应内容。

**后续最小回放设计：** 记录“在第几个仿真 tick，对哪些场景单位下达什么指令”，包括命令类型、稳定场景单位标识、目标单位或位置。通过已有指令入口执行；运行时 object id 需由本次场景建立映射。记录格式带版本，未知格式、配置不匹配和单位缺失明确报错，避免静默套用错误输入。具体格式与入口在认领时按代码确定。

**结果指标：** 指令到动作开始的仿真时间、首次接敌时间、伤亡、完成/超时、非预期停滞时长。选题不需要的指标不采集。性能实验另记固定机器和构建配置、预热方式、采样长度及帧时间分布。

**比较方法：** 先选三个固定 seed，每个条件重复三次作为诊断起点；只有差异不清楚时扩大样本。报告单次结果和范围，不能用九次运行宣称广泛统计结论。固定 seed 不保证 Bullet 逐帧确定性；区分相同 build 内可重复程度和跨改动的行为等价，采用事件、结果与明确容差判断。

**导演隔离：** Sandbox19 已有停滞后强制接触兜底，会改变双方位置和结果。实验须记录其触发；验证自然搜索与导航时应在可控配置下禁用或使用隔离场景，设超时退出，不能把传送带来的接敌视为 AI 成功。开关属于待核对/补充能力。

**验收：** 能用记录恢复相同实验条件，区分完成、失败、超时；对一次单变量变化给出可核对的比较，并明确随机波动与平台限制。事件记录先达到这个目标即可，不等待完整回放才完成阶段。

### M3：做深“发现—共享—响应—搜索”

**问题：** 团队共享在什么条件下帮助未直接看到敌人的队友，又何时产生过期信息或不必要移动？

**最小实验优先落在 Sandbox12：** 两名同队士兵 A/B 与一名敌人；布局使 A 能直接观察敌人，B 不能。敌人按固定实验过程出现、离开视线。先用感知诊断证明遮挡条件，再比较团队共享开启与关闭。

- A 看见敌人时，观察团队信息的写入来源、位置和时效。
- B 未直接看见敌人时，观察它是否因共享事实改变目标或移动。
- 敌人离开视线后，观察最后已知位置与 TTL 的变化。
- 事实过期后，观察 B 是否停止依赖该事实，并按既有树进入后续行为。
- 若现有行为树没有需要的搜索动作，先把它记为独立行为缺口；不要把“有记忆数据”直接当作“有完整搜索策略”。

**开关边界：** A/B 两组只改变实验中的团队信息发布/消费条件，保留直接感知、出生点、能力参数与调度不变。具体开关先核查已有 preset/API；若缺失，局部增加实验配置，避免全局清空团队系统干扰其他机制。

**证据：** 发布事件、B 的直接可见状态、B 消费的信息来源、决策与移动变化、事实失效时间。必要时补一个过期事实的负例。团队来源与自身感知不能混为同一原因。

**验收：** 共享开启时能证明至少一次 B 的响应来自团队信息；关闭时 B 不使用该信息；过期后不继续依赖它。记录收益和代价，不以必须提高胜率验收。专题通过后，再决定是否将行为变化接入 Sandbox19，重新检查指令优先级与自主行为交接。

## 6. 后续专题如何激活

| 主题 | 触发问题 | 最小实验 | 先不展开的内容 |
|---|---|---|---|
| 动态导航 | 路线被改变后单位无法恢复行动 | 一扇门或一个障碍变化后的路径恢复 | 完整世界 streaming、多层大地图 |
| 掩体与战术 | 有危险图，但移动选择缺乏差异 | 两条路线或两个位置的风险/距离权衡 | 通用战术规划器和大量角色职业 |
| 小队分工 | 多人集中执行同一动作造成浪费 | 两个角色分配一项有限任务 | 完整任务规划语言 |
| 多 agent 性能 | 代表性场景出现已测得的瓶颈 | 固定条件下测 100/500/1000 agent，优化一个热点 | 未建立可比较条件的全面多线程化 |
| 数据与工具 | 同类实验反复改代码、配置错误频繁 | 一个 preset 校验或局部参数编辑工具 | 完整 Def/CSV/UGC 编辑器 |
| 模块复用 | 第二场景需要同一能力 | 复用同一服务，记录必要适配 | 为假想用户设计通用 SDK |

以上是能力地图，不是必须全部完成的清单。每次只认领一个问题；明确对学习有价值的专题可独立启动，不要求先证明商业玩法需求。

## 7. 质量与验证设计

| 变化 | 最小验证 | 不能替代的证据 |
|---|---|---|
| 纯文档 | 差异、链接、术语、换行与状态一致性 | 不据此声明代码或运行时已验证 |
| Lua 实验配置/行为 | 语法检查、相关 sample 运行、关键事件与画面 | 静态检查不能证明 AI 行为正确 |
| C++/Lua 接口 | 绑定生成、调用点检查、相关平台构建与 sample | 头文件声明不能证明 Lua 可调用 |
| 指令/观测改动 | Sandbox19 对应自测、目标死亡/过期/重开；相关 AI sample | smoke 不能评价操控和视觉可读性 |
| 性能 | 同机同配置 Release，对照条件与重复测量 | 历史 Windows 数字不能直接作为 macOS 目标 |
| 引擎输入/生命周期 | 条件编译检查、当前平台真实窗口验证 | 未运行的平台明确记录验证缺口 |

代表性回归优先复用 Sandbox8/12/17/19；根据影响范围选取，不要求每次全跑。涉及 FSM 或其他专题再加入对应 sample。遵守 AGENTS.md 的构建、对象位置真源、Lua 生命周期和文本格式约束。

`backlog.md` 中历史 1000 agent 成本用于提示选题，不作为新环境验收阈值。具体性能预算应在固定机器、负载和采样方法后确定。

## 8. 个人项目的执行方式

### 8.1 一个阶段只回答一个主要问题

每个 cycle 写明：问题、最小产物、完成证据、范围之外、下一次复盘条件。规模以几次可用工作时段能形成结果为宜；实际投入未知时不承诺日历工期。

M1/M2/M3 是研究路线的依赖顺序，不一次性同时开工。M1 先补观察缺口；M2 建立最低限度的实验条件；M3 利用这些能力验证团队机制。§1.3 的同一场任务可为研究提供稳定场景，研究设施仍按真实问题补最小能力。

### 8.2 完成、调整与暂停

- 完成：问题得到有证据的回答；结论为无收益、不适合或暂不继续，同样有效。
- 调整：实验过大时缩小问题，记录已得到和仍缺少的证据，不反复追加范围。
- 暂停：记录当前入口、最后可运行版本、未解决问题和恢复第一步。恢复日期可不确定。
- 复盘：完成最小实验、出现实质阻塞或准备换题时进行；可自设日期作为提醒，届时选择继续、缩小或暂停。
- 不强制应用/技术周期交替，不以连续未交付自动判定项目结束，不要求外部玩家或最终品类决策。

### 8.3 阶段记录模板

> 问题：本轮想弄懂什么？
>
> 最小产物：哪个 sample、配置、模块或实验记录？
>
> 变量与证据：改变什么，观察什么，怎样判断？
>
> 范围之外：哪些相邻问题本轮不解决？
>
> 复盘条件：何时检查是否继续？
>
> 结论：已验证、尚未知、恢复/下一步入口。

外部试玩是可选证据。有机会时补充陌生人理解和体验反馈；没有时不阻塞个人实验，也不把作者自测包装成外部验证。

## 9. 文档与知识管理

- 本文：方向、目标、长期能力地图与阶段设计，不维护任务勾选状态。
- `cycle-01.md`：当前阶段的实施范围、已有证据与复盘；后续真正切换 cycle 时归档旧记录并更新入口。
- `backlog.md`：唯一任务勾选清单，记录候选问题和激活条件，不复制历史运行叙述。
- `docs/modules/` 与专项文档：已落地模块的事实与实现约束，变化后同步。
- `docs/memory/`：代码和文档没有直接表达的跨会话经验，避免重复保存路线。
- 实验原始日志与临时输出留在本地；有价值的结论放当前 cycle 或相关模块/perf 文档，说明版本与条件。
- 沿用三份规划入口，不另建一套长期排期；具体实现足够复杂时再形成局部 spec/plan。
