# Sandbox19 视觉与操作体验复核

日期：2026-09-12
范围：根据作者关于目标图差距、命中特效缺失、Agent 动作/滑步、镜头操作的反馈，分析当前工作区与可执行文件。只做分析和取证，不修改运行代码，不提交。

## 结论

当前差距同时来自场景构图与资产、反馈渲染缺陷，以及运动/动画/镜头之间的时间与方向不一致。继续只补墙、贴图和灯光，会让静态截图逐步改善，但不能解决滑步、发枪不协调和转镜头拖手。

上轮几何尺寸、天空接缝、真实投影等修复有实际收益，不能据此判断目标画面或核心体感已经完成。尤其此前文档将“创建枪口焰/命中粒子”写成已完成反馈，证据不足：本轮已确认当前 macOS GL3+ 会跳过该粒子材质的绘制。功能 smoke、自然通关都无法证明这一反馈可见。

| 问题 | 本轮结论 | 证据级别 |
|---|---|---|
| 命中没有特效 | 真实碰撞创建了 BulletImpact，但 Particles/Impact 无 GPU 程序，GL3+ 静默跳过 | 当前二进制断点 + 源码 |
| 移动射击滑步 | 物理速度继续推进，站立射击动作整身覆盖移动动作 | 控制器/动画源码确认 |
| AI 射击时漂移 | 仅在速度平方 >2 时主动减速，近水平速度低于约1.41m/s就停止主动制动 | Lua → C++ 阈值链确认；未测每个Agent停步距离 |
| AI 动作与发弹不同步 | 固定200ms发弹，与最长0.5s的跑→射混合、玩家动画notify时序并存 | 源码确认 |
| 镜头转动拖手 | Q转1秒后，松键仍继续转约29°，约0.5秒才接近最终方向 | 3.5秒内部输入实测 |
| 目标图差距 | 中景内容稀疏、前景围合不足、角色/枪械轮廓与近景材质层次不足 | 目标概念图与当前实机对照判断 |

## 1. 目标图与实机：还缺什么

[目标概念图](assets/sandbox19-p0/target-combat-v2.png) 与本地正面实机截图（`docs/dev-design/specs/assets/sandbox19-visual-20260912/after-entry.png`，验收产物不入库）是不同类型的产物；目标图表达希望达到的视觉关系，不能把生成图的逐像素一致作为现有资源验收。

| 观察项 | 目标图的关系 | 当前主要差距 | 应改变的内容 |
|---|---|---|---|
| 空间与构图 | 近处掩体、箱体、棚架包住玩家；中段交火；后方relay收束视线 | 大片空地占据画面，掩体稀疏且尺寸/间距重复；棚架仅局部形成层次 | 以游玩镜头安排前中后景，调整遭遇区尺度与掩体组合，保持主路/绕行功能 |
| 建筑与道具 | 有厚度、倒角、接缝、结构连接、设备附件与使用痕迹 | 多数为锐利程序盒体；门面大面积靠贴图表达；可见中等尺度结构细节不足 | 补可复用的墙角、门框、连接件和成组设备，而非继续随机增加小物件 |
| 地面 | 大尺度磨损、中尺度接缝、细尺度砂石共同呈现 | v3改善了重复网格，但整体仍平，近景变化不足；平面污迹/接触阴影有贴上去的感觉 | 配对地表颜色/法线与统一真实尺度，控制地表层强度和接触关系 |
| 角色与枪械 | 护甲块面、关节和枪体清楚；白甲、暗部、指示灯分工明确 | 旧士兵/枪械外形与目标不同；黑甲敌人在当前光照下细节弱；枪体细长 | 先修渲染和动作，再校准资产轮廓、比例与材质；单纯加发光/调色不能改变造型 |
| 光照 | 明确主光、可读暗部、建筑与人物稳定接地 | 已有真实投影，但modulative同时压低ambient；少量接触椭圆与真实阴影叠加；精细轮廓仍有限 | 控制阴影与环境光关系，避免重复接触层；先量化性能再升级接收方案 |
| 交火与HUD | 发射、弹道、命中、受击让战斗成立，UI有明确层级 | 当前常见的是长直线曳光；命中粒子没绘制；HUD有较重矩形、长英文状态截断 | 先恢复完整交火反馈，再做信息层级与状态长度收敛 |

场景源码的地面是48×64m，主要长掩体行位于z=-8.5/5.5/23.5，前后间距约14/18m。它保证了通行，但当前相机下会显得空旷。目标图的密度不能只靠加纹理噪声达到；需要一小段完整的“近掩体—交火点—relay”空间，侧看和走近也成立。来源：[sandbox19_scene.lua](../../../bin/res/scripts/samples/sandbox19_scene.lua)。

## 2. 命中特效：已定位到真实渲染缺口

### 调用链存在，绘制没有发生

[PhysicsWorld.cpp](../../../src/HelloOgre3D/sandbox/systems/physics/PhysicsWorld.cpp) 把真实接触点传给 BlockObject/AgentObject。两条碰撞路径均调用 SpawnBulletImpact，创建名为 BulletImpact 的粒子系统。当前断点实际停在 BlockObject.cpp:264，读取到：

- `particle->getNumEmitters()` = 3。
- `particle->getMaterialName()` = Particles/Impact。
- 接触点位于地面，pointA.y=0；粒子不是完全没有创建。

[particles.material](../../../media/materials/particles.material) 的 Particles/Impact 只有lighting/depth/blend/texture配置，没有顶点/片元程序。进一步把断点限定到该材质，在当前可执行文件中捕获到 `noActiveGraphicsShaders=true`，进入 [GL3PlusRenderSystem.cpp](../../../src/Engine/ogre3d_gl3plus/src/OgreGL3PlusRenderSystem.cpp):1650 的静默return。**这是当前macOS特效不可见的已确认原因。**

同一个材质也用于 MuzzleFlash，因此枪口焰受到相同影响。渲染探针还记录 Particles/Bullet、SF_Weapon_Stabilization、SF_Weapon_Thursters 被同类路径跳过；后两者说明部分枪械附属材质也需要核对。没有Windows本轮运行证据，不能直接把该GL根因推广到D3D9。

运行证据：`tmp/sandbox19-experience-audit-20260912/impact-debugger.log`、`impact-skip.log`。第一份的粒子创建/发射器/材质读取成功，后续尝试调用不存在的getMaterial接口失败；第二份独立以渲染pass所属材质限定断点，确认真实跳过。调试进程均已结束，日志中的killed是诊断主动结束，不是崩溃或通关证据。

### 为什么以前看见弹道仍不能证明粒子正常

[WeaponComponent.cpp](../../../src/HelloOgre3D/sandbox/components/combat/WeaponComponent.cpp) 另行创建了一条使用debug_draw的7.5m直线，生存0.22s。它独立于物理子弹，不按真实命中距离裁剪。当前能看见这条线，而Bullet/MuzzleFlash/Impact的粒子材质可能全被跳过。因此“截图有橙色线”不能充当完整枪火链验收。

恢复渲染后仍要处理表现：命中粒子默认只有0.11m；不同距离下可能很小，所有表面又共用同一火花模板。墙体碎屑/尘、金属火花、Agent命中提示应有清楚区别，且位置与法线来自真实碰撞；先修可见性，再调尺寸、寿命、材料类型与受击反馈。

## 3. 角色运动与动画：三个机制在互相打架

### 3.1 玩家允许移动射击，但动画仍是整身互斥

[PlayerController.cpp](../../../src/HelloOgre3D/sandbox/components/control/PlayerController.cpp):337起在射击时继续设置水平速度，却以`!shooting`阻止EnterMoveIntent。[SoldierAnimController.cpp](../../../src/HelloOgre3D/sandbox/objects/animation/SoldierAnimController.cpp):50起让action优先覆盖整个body状态，Shoot映射到站立fire。系统没有上下半身遮罩或移动射击状态。

结果是脚在站立射击姿态里，胶囊仍向前或侧向移动；这条链直接产生滑步。上一轮恢复“射击中可移动”只修正了位移中断，尚未补齐能支持这种位移的动画表现。

非射击移动也存在错配：任意Move意图最终只选择run_forward；速度直接切到maxSpeed，Shift再乘1.75，但动画播放速率不读取实际水平速度。[AgentAnimState.cpp](../../../src/HelloOgre3D/sandbox/objects/animation/AgentAnimState.cpp) 只用固定rate乘dt推进，当前没有步长/速度匹配、急停、转身和足部接触控制。模型即使换新，现有驱动仍会让它滑。

### 3.2 AI“已不算移动”不等于速度为零

[ShootAction.lua](../../../bin/res/scripts/ai/decision/actions/ShootAction.lua):63只在`owner:IsMoving()`为true时调用减速。[AgentObject.cpp](../../../src/HelloOgre3D/sandbox/objects/AgentObject.cpp):442把IsMoving定义成`GetVelocity().squaredLength()>2`。地面近水平运动时，约1.41m/s以下便返回false。

[AgentUtils.lua](../../../bin/res/scripts/agent/AgentUtils.lua) 的Soldier_SlowMovement每次把水平速度乘0.91，且不使用传入dt。速度降到阈值以下后，射击动作不再主动制动，剩余速度交给物理摩擦消除。此时动画已向站立射击切换，所以会出现持续漂移。这是明确的停止语义缺陷；需要测真实水平速度和停步距离，不能用IsMoving=false证明已停稳。

Move/Pursue的cleanup刻意保留速度以支持平滑交接，但ShootAction注释所称“SetVelocity(0)站住”与实际实现不一致。修复应明确交接到移动/射击/待机各自的速度合同，避免为消滑步把所有行为切片都强制刹停，破坏Sandbox6/7/8。

### 3.3 转身、动画混合和实际发弹没有同一时序

AI ShootAction以固定200ms触发ShootBulletAt，600ms作为结束兜底。与此同时，[SoldierAgent.lua](../../../bin/res/scripts/agent/SoldierAgent.lua) 的run_forward→fire混合为0.5s，fire→move也有0.5s；播放器在转移期间同时推进两段动画，没有基于脚步相位对齐。玩家则走fire动画18%位置的shoot_fire notify。两条开火路径用不同的钟。

因此AI可能在身体尚未完成举枪/转姿时已经发弹。ShootAction每次直接`SetForward(toEnemy)`，底层直接替换刚体旋转，没有角速度上限、原地转身或上下身瞄准分工；走路使用0.2方向平滑，进入射击却瞬间朝向敌人。用户看到的突转、动作不协调与这些切换机制吻合。

后续应让实际位移、移动方向、瞄准方向和动作时点共同驱动动画：下半身负责移动/停步，上半身负责瞄准/射击；普通移动先校准实际速度与步频，补转身/停步，再决定是否需要足部IK。优先复用现有骨骼、driver、Blackboard与事件，不必先重写完整动画引擎或采购整套新角色。

## 4. 镜头：控制模型与响应都需要调整

### 4.1 当前只有键盘偏航，鼠标转向没有接入FOLLOW

PlayerController的Q/E角速度是2.5rad/s，约143°/s；默认33ms逻辑步相当于目标角度每次变化约4.7°。FOLLOW模式在OgreCameraController::injectMouseMove中直接返回，所以FREELOOK已有的鼠标灵敏度/平滑参数不会改善Sandbox19的跟随镜头。没有独立俯仰输入，也没有在当前follow实现中做墙/屋顶遮挡探测。

右键在sample中承担地面命令/敌人集火，左键承担选择。这是有价值的战术操作，但尚未与玩家射击所需的精细镜头形成完整输入约定。建议保留命令语义，增加明确的拖动旋转手势与俯仰；若采用右键拖动，必须有点击/拖动阈值与释放消费规则，避免转镜头时误下命令。中键拖动也可避免冲突，Q/E作为辅助。

### 4.2 实测松键后仍继续转约29°

当前候选、后台真实GL窗口、无截图阻塞的3.5秒内部输入：静止玩家，1秒时按Q、2秒时松开，期间用无按键mouse_move事件记录相机方向。FOLLOW忽略这些鼠标位移，因此它们只用于记录。

| 时点 | 实际相机偏航 |
|---|---:|
| 按Q后约0.1s | 2.37° |
| 按Q后约0.5s | 42.64° |
| 松Q时（elapsed=2013ms） | 112.48° |
| 松开约0.2s | 131.59° |
| 松开约0.5s | 139.78° |
| 最终稳定 | 141.80° |

松键后还转约29.3°；约半秒才到最终角度的2°附近。它不是只有主观“有点重”，而是有明显的持续追赶。证据：`tmp/sandbox19-experience-audit-20260912/camera-response.json`和同名运行目录。

[OgreCameraController.h](../../../src/HelloOgre3D/runtime/ogre/OgreCameraController.h):287起用相机位置弹簧追理想跟随位置，再lookAt玩家；平移上还叠加了目标位置低通。用于抑制物理抖动的处理，同时把主动旋转做成了缓慢追赶。应分离主动视角旋转和跟随平移：旋转响应直接、可预测，位置跟随保留少量平滑。

### 4.3 瞄准与屏幕方向还不一致

PlayerController的枪向由目标`m_yaw`生成；WASD移动却读取实际`GetCameraForward()`。实际镜头仍在追赶时，枪向已经到目标角度，移动方向又跟着旧镜头；这会造成边转边射/边横移时的方向错觉。应明确唯一的瞄准方向与屏幕参考，不让三个方向各自滞后。

相机和动画由30Hz仿真驱动，RenderComponent直接拷贝刚体变换，没有逐渲染帧插值；GameManager先更新对象/相机/动画，再推进PhysicsWorld，表现还存在更新相位差。即使GPU更快，当前呈现也不会自动变成连续高频响应。不能只把全局仿真改60Hz，必须保护AI/物理时钟语义并把显示更新与仿真状态插值设计清楚。

## 5. 性能会放大这些问题

前一轮同候选静止机位A/B的周期样本平均cpuFrame约为阴影开30.97ms、关17.50ms，新增开销主要在engineGap而非AI；它会放大镜头/输入的粗糙感。样本不是完整帧序列，不能声称全程稳定32FPS或用它推断发布版上限。

另一个必须先核对的条件是当前Xcode主工程的Release依赖代理仍指向`libogre3d_d.a`等库；依赖Debug配置为-O0，主程序Release为-O3。这个混合构建已记录在[项目经验](../../memory/xcode-release-dependency-proxy.md)。后续性能收敛应先修正/核对Premake生成的Release依赖选择，再做同条件帧时序基准，不能仅凭主target名字宣称完整优化构建。渲染减负也不能替代动画和镜头机制修复。

## 6. 建议的实施顺序与验收

本节是下一轮建议，不表示已实施或已经获准提交。

1. **先恢复真实命中反馈。** 给粒子补完整平台渲染程序，连同枪口焰、子弹和被跳过的枪械部件复核；实际发射/碰撞事件驱动特效。验收应看到墙、地面、Agent的近/远命中，且能关联实际接触点，不能只数粒子或看曳光。
2. **再处理滑步和动作时序。** 修正射击/待机的停止合同、统一发射时点，支持移动与射击的动画组合；由真实水平速度驱动步频与方向，缩短不合适的起停混合。验收直跑、急停、转身、倒退/横移射击、AI追击→射击、取消/死亡/重开，并回归Sandbox6/7/8。
3. **把镜头做成可精细控制的输入。** 明确旋转手势与命令点击边界，支持俯仰，分离旋转响应与跟随平移，统一瞄准参考；补遮挡与渲染插值。重复同一Q释放探针，另外由作者检查连续鼠标输入和追踪目标的感觉。
4. **同步恢复可靠性能基线。** 核对Release依赖，分别测无阴影/有阴影与有/无粒子，保留Tracy和帧时序。按瓶颈减少额外pass、更新/创建成本，不先牺牲全部反馈。
5. **最后用完整战斗切片收敛美术。** 选入口到relay的一段代表性空间，统一围合、掩体尺度、道具组、地面和角色材质。固定镜头、状态、尺寸对照目标关系，并看近景/侧面/移动中的画面；不以道具数量或只看正面截图验收。

上述顺序里，特效是可独立处理的明确渲染缺陷；运动/镜头/性能共同决定核心体感；视觉资产则需要围绕一个已经好操作的战斗切片制作，避免再做一轮只改善截图的局部堆叠。

## 证据边界

本轮读取当前未提交工作区，保留此前全部实现；使用已构建的当前macOS二进制，未重建或修改游戏源码/材质/运行Lua。新增内容为本审计文档与本地诊断脚本/日志。调试器检查不代表运行稳定性测试，内部输入不代表硬件键鼠/真人评价。Windows命中渲染、动画脚底实际滑移距离、鼠标端到端延迟与相机撞墙极限均未在本轮完成测量，后续应按对应问题单独验收。
