# 中继站小玩法重设计：双机交叉行动

日期：2026-09-19。
状态：作者已授权按草案升级，A/B 首个房间已实现为 Sandbox20，随后要求继续 C 阶段三关与体验衔接（见[第二轮记录](../plans/2026-09-19-crossfire-three-encounters.md)）；详见[实施与验证记录](../plans/2026-09-19-crossfire-first-room.md)。作者已试玩当前版本，对场景、模型和射击操作的整体完成度不满意；作者表示直接射击与战术指挥均可接受，优先最容易形成完成度与特色的方向。作者随后明确补充：美术、场景等也需要同步升级；本次范围是玩法与整体视听品质的联合改造。首轮已按机器人、固定镜头、工业庭院与侧击护盾方向落地，作者对新体验的主观验收仍待反馈。

## 1. 判断与范围

当前工程能支撑可运行、可观察、可重复的 AI 场景，P1/P2 功能与历史回归证据继续有效；作者本轮反馈意味着整体体验尚未通过主观验收。不能再仅以“尚待真人试玩”解释差距，也不能把未说明的持续输入、音频或 Windows 分项改为已验。

推荐把产品层收敛为：固定斜俯视镜头、两台低空悬浮机器人、允许暂停下令的一屏战术遭遇。核心是利用敌方朝向和攻击前摇，通过两台单位的位置与时机配合完成侧击。首个样段只含一个房间、一种武器、一种敌人和一次可理解的胜负；成立后才扩到三场手工遭遇。

原第三人称 Sandbox19 与章节 sample 保留作对照及回归。新实验因镜头、控制身份和规则实质不同，使用独立 Sandbox20 入口及 Crossfire 试玩包；旧 Sandbox19 默认开发入口保留。

## 2. 当前 Demo 感的证据与推断

| 观察 | 仓库依据 | 设计含义 |
|---|---|---|

## 3. 一次值得重复的战斗

体验承诺：玩家能看清威胁、安排两台单位，然后看见 AI 准确执行一次自己设计的夹击。

1. 进入一个完整可见的中继站设备庭院。两台己方机器人、中央遮挡体、两条通路和一台护盾哨兵构成第一场。
2. 点击单位或按 1/2 选择，右键地面移动，右键敌人攻击；Space 暂停/恢复计划。常驻自由光标，无需 Alt 切换和手动控制人物转镜。
3. 暂停时每台单位仅保存一条待执行命令，路径和终点可修改；恢复时同一仿真 tick 提交。这里的“同时执行”只保证共同提交，不保证同时到达或命中，不做时间轴、完整动作队列或未来伤害预测。
4. 哨兵正面护盾有清楚的实体外形与地面方向标记。它按实际可见目标选敌，转向有速度上限，射击有可见前摇及短暂朝向承诺；玩家可以让 A 引开朝向，让 B 从另一条路切入侧后。
5. 正面命中表现为护盾闪光和弹开音；有效侧击表现为机体反冲、不同命中音和准确扣血。死亡后关闭火力、短促解体并留下可读残骸，避免长动画阻塞下一步。
6. 胜利与重试立即可用，结算只展示耗时、损伤和侧击结果。先验证不同安排确有结果差异，以及玩家能解释原因；不保证这个提案天然有趣。

首版两台己方单位能力相同，以轮廓标识和数字区分，避免同时引入职业、技能和数值成长。每台单位默认原地警戒，主动追击受下令目标及局部范围约束，避免自动离开玩家安排的位置。没有视野时不能使用隐藏目标位置；指令失败、过期目标和不可达都需清楚表达。

此玩法依赖新增方向护盾与攻击前摇，现有项目尚无该完整机制；现有守卫树、真实视线、导航、转向与命令生命周期可复用。

## 4. 美术与场景升级：与玩法同时交付

作者明确要求场景、美术随玩法一起升级。首个样段必须同时形成新的角色、空间、材质光照、动态反馈和 UI 品质；美术应有独立的可见验收条件。玩法更换、俯视镜头或机器人题材均不自动提高美术质量。

### 4.1 建议的整体风格与第一张画面

候选风格是“有工业结构细节的风格化科幻微缩场景”：轮廓清楚、比例统一、材料克制，精度集中于主体与近中景。这里的简化强调设计选择；主角仍须有完整造型、可读机械结构与可信材质。该风格尚待实机样段验证。

第一张画面建议围绕一座紧凑中继站维修庭院构图：前景是切开的检修台和机器人入场位，中景用设备核心、低墙和侧路形成交战空间，背景由中继塔、带厚度的门厅及连续设施收束。电缆沟、维修标识、管线和局部磨损解释设施用途；以稀疏、有因果关系的细节支持地点感。可见高差优先放在不可行走的背景、基座和轮廓上，首版可行走层仍保持单层。

固定偏航的斜俯视透视镜头、有限缩放是候选构图约束。主要路线、主体轮廓及瞄准方向在最终窗口尺寸下可读；高墙/屋顶通过布局和高度先解决遮挡。整体先核对大块明暗、轮廓和前中后景，再做表面细节。

建议采用暖灰设施、冷暗地面/阴影、青色己方、橙红危险。颜色配合形状/符号，不单靠红绿区分。主光有明确方向，暗部仍能辨认结构；发光面只用于状态与视觉焦点。最终配色由同引擎实机对照确定。

### 4.2 旧资产如何处理

| 层面 | 当前资产处置 | 首个精修样段交付 |
|---|---|---|
| 己方角色 | 旧士兵/枪械及追加背甲保留于旧 sample，作为产品候选时需重新评估 | 一套完整机器人主体、武器与两种身份标识；完整轮廓、面板分区、挂点及移动/射击/受击表现 |
| 敌方 | 旧士兵仅作逻辑占位，不能代表新风格验收 | 一种同风格护盾哨兵，正面、弱点、炮口、转向和攻击前摇能直接辨认 |
| 场景布局 | 现有大院区保留回归用途，新样段重新组织空间 | 一间从进入、交战到出口均有构图的完整庭院，中央与侧路各有明确作用 |
| 建筑与设施 | 现有模块逐件评估比例/材质/细节，适合者重做材质，不合适者替换 | 约 8–12 类模块为初始预算：墙段/墙角/门框、地块/边缘、低掩体、检修台、管线、设备柜与中继核心；实际数量服从画面 |
| 表面资产 | 现有生成贴图可作测试，不能直接当作一致材质套件 | 按实际 shader 支持提供配对的颜色、法线、表面响应与发光数据，统一真实尺度与纹理密度 |
| UI 与特效 | 复用生命周期与状态事实，重新设计产品表现 | 单位卡、计划/执行、目标/路径和结算统一字体、图形、间距、动效；战斗特效按事件强弱分层 |
| 声音 | 现有合成短音保留作工程测试 | 点射、护盾、机体命中、移动、确认和环境底噪的完整分层，支持必要的并发播放 |

本表是制作范围与建议预算，不是已经获得或实现的资产清单。机器人悬浮表现只在单层地面上运行，不表示新增三维飞行导航；运动和碰撞仍须真实。

### 4.3 制作和接入方式

先确定最终镜头下的造型、尺度和材料，再制作/选择一个主角、一个敌人、一组场景模块形成风格基准。独特主角与中继核心值得定制，通用环境可以选同一套模块进行风格适配；资产选择、费用和使用权限在具体候选确定时再核对，本轮没有采购。

脚本生成可服务重复结构、碰撞体和验证；英雄角色与核心建筑的品质要按实际造型判断，不能以生成器可重复输出或网格数量代替美术验收。若现有工具与素材无法做出合格主体，应明确引入成套资产或建模/动画制作投入，避免无限追加外壳维持旧造型。

AI 图像可用于构图、造型探索和颜色贴图试验。法线/粗糙度等技术贴图必须与实际表面和 shader 语义匹配；需要准确细节时由真实模型/材质流程烘焙或制作，并检查色彩空间、切线/法线方向、UV 接缝与平台表现。生成的概念图不等于可用 3D 模型、骨骼、动画或材质套件。

导入小样先检查单位、轴向、原点、挂点、法线/切线、贴图密度、材质分区、碰撞轮廓和导航占地。悬浮/后坐等纯显示偏移不改写物理位置；关键交战轮廓必须与真实命中一致。现有 GL/D3D9 路径先验证需要的明暗、表面反光、阴影和特效；画质需求确有缺口时再局部补渲染能力，每项同时记录成本。

### 4.4 美术质量如何验收

- 静态：用实际游戏分辨率取得进入、交战、出口三个机位；每个机位都有清楚视觉焦点、前中后景和统一材质尺度，角色没有融入背景，墙角/地面没有明显穿插、漂浮或贴片边界。
- 动态：连续展示移动、刹停、转向、短点射、受击和击毁；机械动作有结构关系和清楚节奏，特效既可见又不遮住目标，悬浮不能掩盖导航或碰撞错误。
- 有声交互：在作者真实操作下验证选择/下令、暂停恢复、交火和重试；画面、声音和判定一致，多个声源能分清，界面不与战斗抢注意力。
- 性能与平台：在明确机器、分辨率和画质下测正常交战的连续帧表现；先确定预算再验收，不用旧截图/间隔采样承诺帧率。目标平台分别验证材质、阴影和资产导入。
- 主观质量：作者对场景、角色、动作和交火分别评价，明确最弱项；局部美术认可不能自动提升为整场体验认可。未认可时优先修正对应造型/构图/反馈，保持首个样段范围。

首个精修样段交付应包含可玩版本、对应实机静态画面与一段连续有声战斗。质量目标是玩家从进入第一眼到第一次下令、第一次命中都能感到统一完成度；概念图仅用于交流方向，最终以可执行版本为准。

## 5. 射击和声音仍要精致

自动瞄准减少手动瞄准负担，枪火反馈仍是核心质量门槛。只做一种有辨识度的短点射武器，统一瞄准稳定、前摇、射速、枪口闪光、短弹迹、接触效果、伤害和停火时点。

真实命中与表现使用同一事件依据；护盾拦截、墙体命中、机体受损和击毁必须能区分。枪口/曳光不能穿过先命中的掩体，扣血必须来自战斗判定，镜头震动克制且不影响点选。

声音先补有限多路播放、基础左右声像/距离衰减和优先级，再制作/选用风格一致的点射、金属命中、护盾、机体移动、环境底噪与命令确认声。仅换现有单路 WAV 无法支持多人交火。实施前确定 runtime 后端，不在 Lua 另建声音设备或绕过生命周期管理。

## 6. 首个样段及推进条件

| 顺序 | 交付 | 继续投入的依据 |
|---|---|---|
| A：玩法与美术同步定标 | 一个房间验证夹击规则，同时将一个正式主体、敌人和场景角落导入最终镜头，完成材料/光照/基础动作试验 | 作者能理解战术选择；同引擎画面达到可信的美术方向；非 Soldier 移动/枪口和资产流程可运行 |
| B：完整精修样段 | 把同一房间补成完整环境，统一角色、场景、动作、枪火、声音与 HUD；保留重试 | 静态、动态和真实有声操作同时成立，作者分别认可场景、模型和交火品质 |
| C：小产品闭环 | 同一资产套件构成三场手工遭遇：单塔引导、遮挡绕行、双塔组合；标题、结算、快速重试、设置与独立包 | 选择和失败原因清楚；视觉与交互品质稳定复用；目标平台实际运行 |

第一轮只推进 A/B 的同一房间；作者在首包后追加“继续后续的升级”，第二轮据此推进 C 阶段，主观品质分项仍保留待反馈。玩法试验和美术基准从第一轮同步开展，每轮同时交付可操作结果与实机画面；美术不能被推迟到全部玩法完成后。三场遭遇可暂以总长约 3–5 分钟调试，但不把固定时长当乐趣或完成证明。

如果这个房间仍不好玩，调整护盾转向、敌人前摇、路线和指令响应，或否定该玩法；不靠增加关卡、成长、武器数量来绕过问题。若原生渲染/资产流程被实际证明无法支撑目标，再评估引擎迁移，当前不预设迁移结论。

## 7. 工程边界与验证

- 复用现有 AI driver、Blackboard、导航/LOS、命令终态、事件设施及诊断。普通 Agent/profile 是机器人装配的候选；现有 Soldier 脚本和武器存在骨骼依赖，必须先做无人体骨骼的发射点及移动链探针，不能假设替换 mesh 即可。
- Lua 持有计划中的稳定单位 ID、目标 ID/位置和值；恢复时重新验证存活/路径/可见性。暂停期间不推进 AI/物理/冷却，也不直接把待执行命令写进活跃 Blackboard；目标失效给出失败，重开清掉全部待执行命令和选择。
- 方向护盾、命中和热点运动放 sandbox；相机、输入、绘制、声音后端放 runtime；game/client 装配。Lua 管场景、规则配置和 UI，禁止把护盾免伤只做成 HUD 假效果。
- 有刚体时继续以 PhysicsComponent/刚体为变换真源；显示悬浮/倾斜使用 RenderComponent 的表现偏移，并核对现有接口能力，不虚构刚体或把视觉节点反写仿真。
- 新绑定同步头文件/导出声明/局部绑定/Lua 调用，保持所有权和重开清理；新源文件同步 Premake。保留 Sandbox6/7/8 和当前 Sandbox19 回归。
- 需要实际窗口和作者体验：点选/下令/暂停修改/恢复/失焦/重开；同条件正面/侧击对照；声音并发与空间反馈；默认分辨率及一个较小尺寸。自动化验证规则和生命周期，作者体验验证清楚、顺手和愿意重玩。
- 本文初稿仅设计与静态核对；后续实现及运行证据见上述实施记录。旧开发入口保留，未购买资源、未提交。
