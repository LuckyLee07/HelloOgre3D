# Sandbox19：玩法收敛与整体视觉设计

日期：2026-09-10。依据：用户明确希望同时落实玩法收敛和整体视觉设计，让体验与效果更趋向产品。方向见 [project-direction](../../project-direction.md)，执行状态统一见 [cycle](../../cycle-01.md) 和 [backlog](../../backlog.md)。本文保留设计边界与验收要求，具体实现和证据见 [当前实现与验收记录](../../playtest-relay-2026-09-10.md)。

执行产物入口：[P0审阅稿](../specs/2026-09-10-sandbox19-product-experience-design.md)、[核心玩法一页说明](../specs/2026-09-10-sandbox19-core-loop.md)。用户已明确反馈：“这套玩法与视觉都非常棒，就按照这套实施吧”。伴随式小队指挥、中继站短任务、浅暖工业场景与紧凑 HUD 已获批准，P1–P3 持续实施，无需再次等待方向确认。概念稿与运行证据仍分开验收，实际状态以 cycle/backlog 为准。

## 1. 本阶段目标与边界

围绕一场小队战术任务，形成从进入、准备、观察、下令、战斗到结算与重试的完整体验。画面、UI、交互反馈与玩法共同定义、共同验收。继续服务个人创作与游戏 AI 探索，不引入商业发行、外部玩家人数或固定工期要求。

首版规模以一张小地图、现有两名 AI 队友、一项主要任务为上限起点。优先完成一场有明确选择和反馈的遭遇战；采用两个接敌段、每段两名敌人，清场后抵达中继入口集合；旧三波仅保留历史记录。不预设新增兵种、成长系统、联机、通用编辑器或更大世界。

已批准的范围如下，参数继续通过真实运行调整：

- 题材与美术：浅暖工业中继站，单层地图与紧凑战术 HUD。
- 任务：清除两段守卫，指挥官与至少一名存活队友在中继入口集合；没有交互占点条。
- 镜头：较高第三人称跟随，保留指挥官实体，使用相机平面移动与有限缩放。
- 命令：集火、集结和入口撤回各自维护完成、失败、替换与取消语义。

## 3. 同一场任务的体验与画面合同

建议的核心体验：观察战场，给少量自主 AI 队友下达关键命令，通过位置、目标和时机改变结果。自动攻击等基础执行由 AI 承担；玩家应能理解命令是否生效、何时结束以及为何无法完成。

| 环节 | 玩法交付 | 视觉与 UI 交付 | 共同验收 |
|---|---|---|---|
| 准备 | 清楚的任务目标；建议主动开始 | 能辨认路线、队友和目标区域的初始构图 | 不看源码也知道身份、目标和开始方式 |
| 观察 | 提供有意义的位置或接敌选择 | 镜头、场景轮廓、光照层次和敌我识别 | 主要战况可见；必要信息不只依赖颜色 |
| 指挥 | 可靠选择、目标指定及命令生命周期 | 队友卡、指令栏、落点/目标标记、接受或拒绝反馈 | 下令有及时、准确反馈；UI 点击不误触战场 |
| 交战 | 有观察与修正窗口，结果来自真实战斗 | 射击、命中、受击、死亡的动画/声音/特效 | 能判断谁在攻击谁、何时受损，特效不遮关键目标 |
| 暂停与恢复 | 仿真、指令 TTL、波次计时语义一致 | 暂停、必要设置与操作提示 | 暂停时不继续消耗战斗时间，恢复无命令突变 |
| 结算与重试 | 准确原因、可恢复的重开 | 与 HUD 一致的结算画面与按钮反馈 | 无旧选择、命令、UI 或音效残留 |

强制接触导演必须记录。在目标体验中出现突兀重定位时，优先通过布局、出生点和可解释的场景规则解决；不得直接删除兜底后将超时当作完成。自然胜负、导演干预、合成状态机测试分别报告。

## 4. 首批可审阅产物

1. 一页玩法说明：玩家身份、主要目标、基本循环、三类命令规则、失败条件和重试方式；明确尚未验证的取舍。
2. 三张目标画面：正常战斗、选中队友并下令、任务结算。统一镜头尺度、环境风格、HUD、字体和色彩；标为设计稿，不能算游戏截图或运行证据。
3. 视觉规范与资源清单：环境/角色轮廓、主光、材质、敌我及选中语义、字号层级、间距、图标与交互状态；标明复用、制作或替换，以及来源、许可和预计集成成本。付费资源不作默认依赖。
4. 能力缺口清单：相机、输入、UI 渲染、光照、音效与特效按“已有并核实 / 需适配 / 待查证”记录。目标画面中的效果逐项对应可行方案；无法实现时修改方案，不留下不可兑现的效果承诺。

建议 HUD 分区：上方任务信息、左下队友状态、下方情境命令、场景内短暂标记；雷达仅在镜头外信息确有需要时占据固定空间。详细诊断按需打开。实际布局由真实视角与长文本测试确定，不将该分区当成固定像素规格。

## 5. 推进顺序与依赖

| 阶段 | 预期产物与实现位置 | 依赖 | 退出证据 |
|---|---|---|---|
| P0：共同设计 | 上述玩法说明、三张画面、资源规范；同一遭遇战的当前画面和操作基线 | 现有 Release 场景可启动 | 能说明画面如何服务操作；记录审阅意见与待验证决策 |
| P1：游戏内第一版 | 一个完整可玩区域与正常战斗 HUD；`Sandbox19.lua`、preset、场景资源、UI 视图；必要相机适配 | P0 给出可实现方向 | 同视角实际截图与目标稿对照；可选择、下令、观察接敌，记录差异 |
| P2：整场体验 | 指令规则、准备/任务/暂停/结算；命令条件、场景编排、UI 生命周期；补齐交战反馈 | P1 操作与画面成立 | 普通完整对局、不同策略小规模比较、失败反馈、重开与持续交互证据 |
| P3：完成度收口 | 材质/光照/声音/动画一致性、多分辨率、设置、独立包和必要性能修复 | P2 流程可玩 | 目标平台独立目录运行、真实截图和短视频、退出与重开回归 |

P1 就应包含代表性的美术与 UI 质量，不把所有美术推迟到 P3。每阶段都围绕同一任务迭代，不同时铺开第二地图或第二套 AI 系统。主观选择需要作者反馈时，呈现具体画面或可运行对比；不以工具无反馈当作作者认可。

M2 只按需提供 preset、seed、版本、策略、结果和导演介入记录；完整录制回放及 M3 团队实验不阻塞本阶段。无需证明指挥必胜，但须能用证据解释至少一种选择如何改变行动过程；没有差异时先修正关卡或操作设计。

## 6. 工程落点与风险边界

- Lua 负责场景规则和 UI 业务；应用流程逐步从 `Sandbox19.lua` 分离为职责明确的局部模块，不先扩建通用框架。
- 相机、输入和绘制适配留在 runtime；AI、导航与战斗事实从 sandbox 读取，UI 不运行第二套感知或决策。
- 正式 UI 可优先评估已有 FGUI 包与 Ctrl/Model/View/AutoGen 链；先验证一个队友卡的渲染、输入拦截和销毁。当前 SandboxUI 可用于过渡。模块文档记录过程序化裸 FGUI 对象不渲染的问题，不可据工具名假设新 HUD 自动可用。
- 如果采用 FGUI，实施前读 `docs/fgui/fairygui-autogen-workflow.md` 与生产 gate；不得在 Lua 长期保留底层裸指针。观察数据继续只保留稳定 id 和值，死亡/重开同步清理。
- 若补 C++/Lua API，同步头文件、导出声明及其引用、局部绑定 cpp 和调用点；遵守现有 tolua 全量生成禁令，新增编译文件改 Premake，ABI 改动 clean rebuild。
- 只为明确画面目标局部调整资源或渲染适配；保留性能埋点，用固定机器、同场景和同画质记录改前改后成本。不从历史平台数字推定新预算。
- 每个实际改动按模块选择回归；共享控制或 AI 变化保留 Sandbox6/7/8，团队/战术变化检查相应 12/17/18。产品任务的视觉完成不能替代章节正确性。

## 7. 验证与交付口径

实施默认先在可用的 Windows Release 环境验证，并记录硬件、窗口尺寸、构建和画质；macOS 条件编译同时检查，可运行环境具备时再补平台实测。计划不承诺未执行的平台 PASS。

首轮布局建议检查 1280×720 与 1920×1080，以及缩放/窗口调整后的输入坐标、文字裁切和目标遮挡。持续移动、拖框、镜头转向必须有真实交互证据，限时 smoke 不代替手感验收。

提交本阶段成果时分别报告：静态/语法检查、平台构建、普通运行、合成自测、实际视觉与交互。保留正常战斗、下令、结算的实际截图及一段连续操作记录；对照设计稿说明已兑现效果和剩余差异。作者体验可以证明个人偏好，不能冒充外部用户研究。

独立包从开发目录之外启动，验证资源、设置写入、重新启动、结算重开和正常关闭；打包后的游戏仍应能按需打开 AI 诊断。尚未定位的历史 NaN 单独保留，不因本阶段短时通过关闭。

完成条件：一场任务能顺畅开始、操作、结束和重试；画面与 UI 有统一风格且关键状态可读；至少一种指挥选择产生可解释的过程变化；实际运行兑现目标画面的核心效果；已知缺口与支持平台准确记录。
